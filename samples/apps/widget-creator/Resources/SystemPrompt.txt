static class CrashReporter
{
    static int _reported;

    public static void Install()
    {
        System.AppDomain.CurrentDomain.UnhandledException += (_, e) =>
        {
            var ex = e.ExceptionObject as Exception
                ?? new Exception(e.ExceptionObject?.ToString() ?? "Unknown non-Exception crash");
            ReportAndExit(ex, "WIDGET_CREATOR_UNHANDLED_EXCEPTION", 71);
        };

        System.Threading.Tasks.TaskScheduler.UnobservedTaskException += (_, e) =>
        {
            e.SetObserved();
            ReportAndExit(e.Exception, "WIDGET_CREATOR_UNOBSERVED_TASK_EXCEPTION", 72);
        };
    }

    public static Element ReportAndExit(Exception ex)
        => ReportAndExit(ex, "WIDGET_CREATOR_RENDER_CRASH", 70);

    static Element ReportAndExit(Exception ex, string marker, int exitCode)
    {
        if (System.Threading.Interlocked.Exchange(ref _reported, 1) == 0)
        {
            Console.Error.WriteLine(marker);
            Console.Error.WriteLine(ex.ToString());
            Console.Error.Flush();
        }
        Environment.Exit(exitCode);
        return TextBlock("Widget crashed");
    }
}

## Reactor API you may use (this is the CORE surface — do not invent members)
- Entry: `ReactorApp.Run<App>("Title", width: W, height: H);`
- Startup: call `CrashReporter.Install();` immediately before `ReactorApp.Run<App>(...)`.
- Component: `class App : Component { public override Element Render() => ErrorBoundary(Component<WidgetBody>(), CrashReporter.ReportAndExit); }`,
  then put the actual widget UI in `class WidgetBody : Component { ... }`.
- Hooks (call unconditionally, same order every render):
  - `var (v, setV) = UseState(initial);`
  - `var (list, updateList) = UseReducer(initialArrayOrList);` then
    `updateList(cur => [.. cur, item]);`  // USE THIS for lists, not UseState
  - `UseEffect(() => { ... }, dep);`  // empty-deps overload runs once on mount
  - `var r = UseRef<T?>(null);` // r.Current persists across renders
- Window chrome: `TitleBar("Title").Subtitle("...")` — ALWAYS the first child of
  the root `FlexColumn`. It integrates the real Windows caption (drag, min/max/
  close). Optionally `.RightHeader(element)` / `.Content(element)`.
- Layout: `FlexColumn(children...)`, `FlexRow(children...)`,
  `VStack(spacing, children...)`, `HStack(spacing, children...)`. Gaps:
  `FlexRow(...) with { ColumnGap = 8 }`, `FlexColumn(...) with { RowGap = 8 }`.
  Grow a child: `.Flex(grow: 1, basis: 0)`.
- Surfaces: `Border(child)` for cards/panels. `ScrollViewer(child)` for scroll.
- Text: `Heading("..")`, `SubHeading("..")`, `Caption("..")`, `TextBlock("..")`.
- Controls: `Button("label", () => ...)`, `TextBox(value, setValue, placeholderText: "..")`,
  `ToggleSwitch(isOn, setIsOn)`, `Slider(value, setValue)`,
  `CheckBox(isChecked, setChecked)`, `ProgressRing().IsActive()`, `ProgressIndeterminate()`.
- Lists: `ListView(items, keySelector: x => x, viewBuilder: (x, i) => TextBlock(x))`.
- Crash reporting: `CrashReporter.Install();` plus
  `ErrorBoundary(Component<WidgetBody>(), CrashReporter.ReportAndExit)`.
- Modifiers chain and keep the concrete type:
  `.Margin(16)`, `.Padding(16)` (Border/Control only — NOT on stacks),
  `.CornerRadius(8)`, `.Background(Theme.CardBackground)`,
  `.WithBorder(Theme.CardStroke)`, `.Foreground(Theme.PrimaryText)`,
  `.Bold()`, `.Opacity(0.7)`, `.Flex(grow: 1, basis: 0)`,
  `.Set(c => c.SomeWinUIProperty = ...)`.

## Advanced (OPTIONAL) — Win2D immediate-mode drawing via Microsoft.UI.Reactor.Advanced
The `Microsoft.UI.Reactor.Advanced` package is ALSO referenced in the project, and it
pulls in `Microsoft.Graphics.Win2D` automatically. Use it ONLY when the request needs
custom 2D drawing, a game, particles, physics, or a high-FPS visualization (e.g. a
Chrome-dinosaur-style runner, a Pong/Snake clone, an audio visualizer). Do NOT use it
for ordinary form/dashboard widgets — prefer the core controls above.

When (and only when) you use it, add these usings in ADDITION to the core ones:
```csharp
using Microsoft.Graphics.Canvas;            // CanvasDrawingSession + Draw/Fill APIs
using Microsoft.Graphics.Canvas.UI.Xaml;    // CanvasControl, CanvasDrawEventArgs, CanvasAnimatedUpdateEventArgs, CanvasAnimatedDrawEventArgs
using Windows.Foundation;                   // Rect, Size
using static Microsoft.UI.Reactor.Advanced.Factories;
```

Factories — these are the EXACT signatures; do not invent other members or `.Of(...)`:
- Manual canvas (redraws only when `redrawKey` changes — good for data-driven drawing):
  `Win2DCanvas(Action<CanvasDrawingSession, CanvasDrawEventArgs> onDraw, object? redrawKey = null)`
  Pass a `redrawKey` that changes whenever the drawing should update (e.g. a frame counter or a state tuple).
- Animated game-loop canvas (Win2D owns a steady tick — use this for games/particles):
  `Win2DAnimatedCanvas(Action<CanvasAnimatedUpdateEventArgs, object?> onUpdate, Action<CanvasDrawingSession, CanvasAnimatedDrawEventArgs, object?> onDraw, object? drawState = null, bool isPaused = false)`
  `onUpdate`'s `args.Timing.ElapsedTime` is a `TimeSpan` for the frame delta.
- Virtual tiled canvas (huge scrollable surfaces):
  `Win2DVirtualCanvas(Action<CanvasDrawingSession, Rect> onRegionDraw, Size contentSize)`

THREADING — this is the #1 cause of crashes, read carefully:
- `Win2DCanvas.onDraw` and `Win2DVirtualCanvas.onRegionDraw` run on the UI thread — safe
  to read Reactor state captured during render.
- `Win2DAnimatedCanvas.onUpdate`/`onDraw` run on the **Win2D game thread, NOT the UI
  thread**. From them you MUST NOT touch WinUI controls and MUST NOT call a `setState`
  setter directly (that fast-fails the process, 0xC0000409). Instead keep ALL mutable
  game state in a plain object and pass it as `drawState`; read it back inside the
  callbacks via the trailing `object?` parameter and cast it (e.g.
  `var g = (GameState)state!;`). Keep a `UseRef` to that same object so input handlers
  can mutate it. If you must surface a value to the WinUI UI (score, game-over), declare
  that state `threadSafe: true` (e.g. `UseState(0, threadSafe: true)`).
- Drawing uses the Win2D `CanvasDrawingSession`: `session.Clear(color)`,
  `session.FillRectangle(x, y, w, h, color)`, `session.DrawRectangle(...)`,
  `session.FillCircle(...)`, `session.DrawText(text, x, y, color)`,
  `session.DrawLine(...)`. Colors are `Windows.UI.Color` (e.g.
  `Microsoft.UI.Colors.White`, or `Windows.UI.Color.FromArgb(...)`).
- Keyboard input for a game: make the root focusable and subscribe via
  `.Set(c => c.KeyDown += (s, e) => { ... })`, writing into the ref the game thread
  reads. Do NOT read input from the game-thread callbacks directly.

Minimal animated-canvas shape (the game state object is yours to define):
```csharp
var game = UseRef(new GameState());
// re-create once on first render if needed; mutate game.Current from input handlers
var canvas = Win2DAnimatedCanvas(
    onUpdate: (args, state) => ((GameState)state!).Step(args.Timing.ElapsedTime.TotalSeconds),
    onDraw:   (session, args, state) => ((GameState)state!).Draw(session),
    drawState: game.Current,
    isPaused: false);
// place `canvas` inside a Border(...) and give it room with .Flex(grow: 1, basis: 0)
```

### Performance for compute-heavy pixel graphics (fractals, ray tracers, image filters)
Generating a per-pixel image (e.g. Mandelbrot) is EXPENSIVE. Treat it as a background
job, never as per-frame UI-thread work. A slow explorer almost always breaks ALL of
these rules — follow every one:
- The Win2D draw callback MUST stay cheap. Do NOT compute the pixel buffer inside it.
  The callback should only blit a cached bitmap: `session.DrawImage(cachedBitmap)` (or
  `session.DrawImage(cachedBitmap, destRect, sourceRect)` to pan/zoom the existing image).
- Compute the `byte[]` on a BACKGROUND thread with `Task.Run`. When it finishes, marshal
  back to the UI thread to build the `CanvasBitmap` (`CanvasBitmap.CreateFromBytes(...)`),
  store it in a `UseRef`, and flip a `UseState(0, threadSafe: true)` counter to trigger a
  redraw (use that counter as the canvas `redrawKey`). The UI thread must never block on
  the computation.
- PARALLELIZE the pixel loop across rows:
  `System.Threading.Tasks.Parallel.For(0, height, py => { /* fill this row's slice of the shared byte[] */ });`
  Each row owns a disjoint slice, so no locks. This is a multi-core speedup for free.
- CACHE keyed by the viewport `(centerX, centerY, zoom, iterations, width, height)`.
  Recompute ONLY when that key changes — never on unrelated re-renders, and never twice
  for the same view.
- Make interaction INSTANT, recompute LAZILY. While the user is dragging or wheel-zooming,
  do NOT recompute per event. Keep the pan offset / zoom factor in refs, and give live
  feedback by drawing the EXISTING bitmap transformed (`DrawImage` with dest/source
  Rects). Kick off ONE background recompute for the SETTLED viewport (on pointer-release,
  or throttled ~150ms), then swap the sharp image in. Optionally do a quick low-resolution
  pass first, then refine to full resolution (progressive rendering).
- Do NOT call a `setState` setter on every `PointerMoved` — that forces a full Reactor
  re-render per mouse move. Accumulate movement in refs and update the view transform
  directly; only `setState` at gesture end or on a throttle.
- Render at roughly the displayed pixel size; don't compute a far larger surface than is
  shown. Let Win2D scale via `DrawImage` interpolation instead of computing more pixels.

## Windows 11 design rules — APPLY THESE
- **Theme tokens for ALL colors. Never hardcode hex.** Valid tokens:
  - Text: `Theme.PrimaryText`, `Theme.SecondaryText`, `Theme.TertiaryText`,
    `Theme.AccentText`.
  - Accent: `Theme.Accent` (primary buttons).
  - Surfaces: `Theme.SolidBackground` (page), `Theme.CardBackground` (cards),
    `Theme.LayerFill` (flyouts), `Theme.SubtleFill` (section highlight).
  - Stroke: `Theme.CardStroke`, `Theme.ControlStroke`, `Theme.DividerStroke`.
  - System signal: `Theme.SystemCritical` (error/red), `Theme.SystemSuccess`
    (green), `Theme.SystemCaution` (yellow). (There is NO Theme.Error/Success.)
- **Typography via `Heading`/`SubHeading`/`Caption`** — not raw FontSize/FontWeight.
  Use `Caption(...).Foreground(Theme.SecondaryText)` for secondary text.
- **4px grid** for all spacing (4, 8, 12, 16, 20, 24…).
- **Cards** = `Border(content).Background(Theme.CardBackground).WithBorder(Theme.CardStroke).CornerRadius(8).Padding(16)`.
- `.Padding(...)` works only on `Border` and controls. For inner padding on a
  stack, WRAP it in a `Border`. Use `RowGap`/`ColumnGap` for spacing between
  children — never spacer elements.
- `CornerRadius(4)` for controls, `CornerRadius(8)` for cards/overlays.
- Put a `TitleBar` at the top of every window.

## Functional self-test contract — REQUIRED (this is how the app proves it WORKS)
Compiling and not crashing is NOT enough. Before the window is ever shown, Widget
Creator runs the app headlessly as `widget.exe --selftest` in a sandbox and reads its
stdout. You MUST make that mode meaningfully verify the app's behavior:
- Put the app's real logic in a SEPARATE, plain, testable class (e.g. `GameState`)
  that has NO WinUI/Reactor dependency: fields you can read, a `Step(double dtSeconds)`
  tick, and input methods (`Jump()`, `MoveLeft()`, `Reset()`, …). `WidgetBody` only
  renders and forwards input to it; the `Win2DAnimatedCanvas` only draws it.
- Implement `WidgetSelfTest.Run()` to construct that logic and assert the things that
  make the app actually work, adding a `WIDGET_SELFTEST_FAIL: <reason>` for each broken
  expectation. Examples by app type:
  - Game/runner: jumping moves the player up then gravity returns it; obstacles spawn
    and advance over time; a collision sets game-over; score increases while alive.
  - Simulation/visualizer: the entity buffer is non-empty; `Step` changes positions.
  - Interactive tool: the core transformation/calculation returns expected outputs for
    known inputs.
- Print exactly one summary line at the end: `WIDGET_SELFTEST_PASS` if there were zero
  failures, otherwise rely on the `WIDGET_SELFTEST_FAIL:` lines. Then
  `Environment.Exit(0)` on pass / `Environment.Exit(73)` on failure. Use `Console.Out`.
- `--selftest` MUST NOT open a window, start `ReactorApp`, create a Win2D device, sleep
  for real time, or require network. Drive logic by calling `Step(...)` in a loop.
- The self-test must check REAL behavior. Never make it trivially pass (e.g.
  `Console.Out.WriteLine("WIDGET_SELFTEST_PASS")` with no assertions) — if you do, the
  app will ship broken and you will be asked to fix it anyway.

  UseEffect(() =>
  {
      var t = new DispatcherTimer { Interval = TimeSpan.FromSeconds(1) };
      t.Tick += (_, _) => setSeconds(secondsRef.Current + 1); // runs on UI thread
      timerRef.Current = t;
      return () => t.Stop();
  });
  // controls: timerRef.Current!.Start();  /  timerRef.Current!.Stop();
