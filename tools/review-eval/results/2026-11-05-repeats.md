# Reactor review-model repeatability study: 2026-11-05

## Result

**Five fresh, uncapped reviews per model reinforce GPT-6.1 Sol as the next
Reactor correctness-review evaluation baseline.** On this snapshot it found
more of the three known runtime defects per run, at much lower recorded cost,
than the other candidates. This is a within-case result, not a statistically
established repository-wide ranking.

All **20 reviews completed**. None found the third known runtime defect.
Repeating the same combined review did not eliminate that shared blind spot.

Neither observation warrants replacing the distribution
with a model's best run.

## Other findings and review quality

**Zero reference runtime hits does not mean zero useful findings.** Findings
outside the frozen reference were investigated, not automatically marked false.
They were not retroactively added to the primary denominator.

| Model | Known-label findings | Additional source-supported findings | Unsupported | Out of scope | Duplicate | Unresolved |
|-------|----------------------|--------------------------------------|-------------|--------------|-----------|------------|
| GPT-6.1 Sol | 7 | 3 | 0 | 0 | 0 | 0 |
| GPT-6 Astra | 5 | 1 | 0 | 0 | 0 | 2 |
| Claude Opus 5.5 | 3 | 1 | 1 | 4 | 3 | 5 |
| Claude Sonnet 5.5 | 0 | 2 | 1 | 7 | 1 | 7 |

Counts are finding occurrences across five runs, not independent defect totals.
The Opus known-label count includes R1 once and the missing disposal-contract
documentation, D1, twice.

All 20 reviews missed **all five reference test-oracle gaps**. Only Opus found
one of the two reference documentation gaps: D1 in 2/5 runs. None found the
incorrect spec-section citation, D2. Security and packaging had no
reference-positive cases and remain unmeasured.

The seven additional source-supported occurrences cover five mechanisms:

| Mechanism, outside the frozen labels | Reported by | Evidence status |
|-------------------------------------|-------------|-----------------|
| Missing deferred true/false/true re-arm test for pending-table removal | Opus once; Sonnet once | Source-supported coverage gap; mixed broader requests stayed unresolved |
| Owner set retains a never-loaded anchor after an abandoned partial mount | Sonnet once | Source-supported error-fallback retention path |
| Native `Closing` cancellation leaves a blank, untracked modal after retirement | Sol twice | Frozen Reactor source plus documented/native WinUI cancellation behavior |
| Early retirement prevents later navigation-page unmount from reaching dialog content | Sol once | Source-supported navigation teardown regression |
| Throwing root cleanup skips the component sweep after dialog content was detached | Astra once | Source-supported no-handler exception path |

These are static/source adjudications, **not newly executed WinUI
reproductions or maintainer-confirmed issues**. Native close cancellation was
checked against the public [WinUI implementation at an immutable revision](https://github.com/microsoft/microsoft-ui-xaml/blob/8463f45162149de0ec3ad7df752596893fe3e13e/dxaml/xcp/dxaml/lib/ContentDialog_Partial.cpp#L480-L559)
and the [documented Cancel property](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.contentdialogclosingeventargs.cancel?view=windows-app-sdk-1.8).
That supports the mechanism; it is not a binary-level reproduction against the
historical Windows App SDK package.

The recurrent native-exception-during-window-close hypothesis remains
unresolved: its conditional control flow is correct, but an actual trigger for
those particular WinUI calls was not established. Two Astra reports raised
another unresolved contract edge: whether disposal during an ordinary
dismissal's content cleanup must cancel its pending `OnClosed` notification.
Composite coverage requests with partly unverified claims were conservatively
left unresolved. Duplicate test requests for a report's own native-exception
hypothesis were not counted as separate defects.

Adjudicated finding-precision bounds, treating unresolved findings as all
incorrect versus all correct and excluding duplicates, are Sol **100-100%**,
Astra **75-100%**, Opus **28.6-64.3%**, and Sonnet **11.8-52.9%**. These are
descriptive bounds under this source-based adjudication, not measured
population precision or false-positive rates on clean PRs.

### Output-format compatibility

Nineteen reports satisfied the exact JSON schema. Opus repetition 3 returned
introductory prose followed by a complete, otherwise valid JSON report. The
recorder initially classified it as incomplete and exited nonzero after all
workers finished. A presentation-only parser correction recovered that same
saved response: **no extra inference or retry**.

Strict schema compliance remains recorded as **4/5 for Opus, 5/5 for each other
model**. All twenty reports contain all seven coverage entries and can be
quality-scored. Recovery preserved the original result, and the normalization
is explicit rather than silently treating that response as schema-exact.

## What should change

1. Keep **Sol as the local correctness-review candidate and next evaluation
   baseline**, while honoring configured host/user model preferences. The
   repeated known-defect/cost result does not support a blanket promotion of
   Opus to deep reviews.
2. Keep Opus as an available challenger, not an excluded model. It contributed
   documentation observations Sol missed. That is possible complementarity,
   not a measured cross-family verification benefit.
3. Do not assume repetition alone fixes coverage. R3 and all five oracle gaps
   survived every review. A focused oracle-review pass and prompt/routing
   changes need separate, controlled experiments.
4. Before claiming general defaults, evaluate another untouched PR and repaired
   controls. Five samples of the same PR estimate within-case variability,
   not five independent PRs. Effort levels, specialized dimensions and the
   end-to-end multi-agent skill remain separate variables.

No additional paid runs were started, and the historical PR was not modified.
